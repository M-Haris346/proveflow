### Why BIPIA is attack-files-only (corrects the 2026-11-10 decision)

The earlier decision kept Email QA, Table QA and Code QA because their source data "ships
in-repo", and dropped only Web QA and Summarization. Shipping in-repo does not change an upstream
license. The LICENSE names Table QA's upstream (WikiTableQuestions) and Code QA's upstream (Stack
Exchange) as **CC BY-SA 4.0**, a share-alike license whose obligations would attach to a derived
corpus.

proveflow does not need any QA context: it needs PAYLOAD text, and the twin generates its own
tool results. Taking only the four attack files — BIPIA's own authored attack text, which is not
among the three carved-out datasets and so remains under the repo's MIT — removes CC BY-SA from
this project entirely. No share-alike obligation attaches anywhere.

### Corpus payloads carry their own endpoints

Upstream attack texts name real-looking addresses and URLs of their own (LLMail-Inject rows, for
example, instruct an agent to mail a third-party address). CLAUDE.md's "no real exfil endpoints"
rule governs payloads **proveflow authors**, not the upstream text of a corpus record, which is
never edited. What makes ingesting them safe is that the sink sandbox is always ON in twin mode
and no sink call ever leaves the machine. Record this where the loader lives, not only here.

### Per-record requirements (Phase 6 step 3)

Every normalized corpus record carries: `source_dataset`, `source_id`, `license` (the license of
THAT record's source, which for BIPIA attack files is MIT), `sha256` of its text, the dataset
revision pin (git commit / HF revision), and the fetch checksum. Pins are chosen at ingest time
and recorded in this file.

**AgentDojo scope, measured, not hand-picked.** A tree scan at the pin found 12
`injection_tasks.py` files (55 goals); a scan of all 99 Python files under `src/agentdojo`
found injection-task registrations in the 11 default-suite files and nowhere else. The 12th,
`examples/counter_benchmark/` (1 goal), is an example suite, not the benchmark, and is not
fetched. Later suite versions do NOT mostly repeat v1: of their 27 goals only 5 match a v1
goal under the dedup key. They are REVISIONS (`task_suite.update_injection_task(version)`)
and, for workspace, 8 new tasks (`new=True`). So AgentDojo is ingested AS OF upstream's
newest benchmark version, v1.2.2, by upstream's OWN rule (`task_suite.py`
`get_version_compatible_items`: per task, the highest version <= the suite's version), with
the PER-SUITE versions read from upstream's pinned table (`load_suites.py`): workspace
1.2.2, travel 1.2.0, banking 1.2.2, slack 1.2.0. A uniform 1.2.2 target gives the IDENTICAL
set at this pin (same task ids, versions and texts; measured), but upstream's table is what
is used, so a later pin cannot diverge silently. Reconciliation: 55 goals in 12 files; minus
the example's 1 = 54 in the 11 default-suite files (27 in v1, 27 later) = 35 distinct tasks
+ 19 superseded revisions (banking 8, travel 4, workspace 7); 35 = the 27 v1 tasks + 8 new
workspace tasks. Per suite: banking 9 (tasks 0-6 and 8 at 1.2.0, 7 at 1.0.0), slack 5 (all
1.0.0), travel 7 (0, 1, 4, 6 at 1.0.0; 2 at 1.2.0; 3, 5 at 1.1.2), workspace 14 (1, 2 at
1.0.0; 0, 4, 5 at 1.1.2; 3, 6-10, 13 at 1.2.0; 11, 12 at 1.2.1). 0 unresolved, 0 above
target.
